# ForWin 三阶段改进计划

**日期：**2026-09-09  
**源码基线：**`Ctwqk/ForWin@521228871a5752ebe8572c057caa9f4944bb0295`，本轮重新核对默认分支后未变。  
**状态：**用户于 2026-09-09 批准实施的当前路线图。各工作包的实现、测试与部署状态单独记录；本文件不宣称阶段验收通过。  
**目标：**先稳定实现无需读者评论的自动长篇生产，再通过消融降低复杂度，最后补齐反馈驱动的连载迭代。  
**架构：**保留 BookState DB Canon 的接纳权、现有持久任务与发布系统；补齐不可变版本、发布冻结、历史修订核验及存稿限制。小说 Git 是可重建的版本展示/导出层，不是第二套运行真值。  
**技术边界：**复用 Python、SQLAlchemy/PostgreSQL、现有任务/outbox/review/publisher；不新建独立监督 Agent、消息中间件或通用工作流平台。  
**执行方式：**本计划确定产品契约、任务边界与验收。实施时每个工作包单独完成失败复现、最小实现、回归和代码评审；不要把全部工作放入一个大 PR。

## 2. 全局不变量

1. 章节的稳定身份与内容版本是两件事；旧提交不得通过改成负章节号来保存。
2. 已对读者公开的章节版本不可被普通 retry、改稿、世界编辑 proposal、回放、Git revert 或后台任务替换。
3. 接纳候选修订前，原 accepted 主线继续有效；验证失败不得让原章节变为 planned 或留下半套 Canon。
4. 所有正式接纳仍经过唯一 Canon 入口。新增验证是该入口的前置条件，不新增平行接纳入口。
5. 发布、修订与生成的关键写入受持久版本号和数据库并发约束保护；UI 判断与本地 Git hook 均不是最终强制点。
6. 正文版本、抽取出的状态增量、计划版本、发布载荷与回执必须可追溯到同一内容身份。
7. 外部结果未知不等于外部未发生。未知发布结果必须核对，不能超时后直接解除保护或重新发送。
8. 评论为零时可正常规划、写作、接纳及发布；等待评论不能成为自动生产的硬依赖。
9. 安全停止属于正确行为；内容失败不能靠无限重试、自动改阈值或强行放行伪装成自主成功。
10. 每个实验/发布候选绑定源码提交、镜像摘要、有效策略与模型配置。中途热修复后的运行不能继续作为原候选通过证据。
11. Git 导出失败不回滚已接纳 Canon；Git 也不得绕过 Canon 改写业务事实。
12. 当前文档必须同时区分现行实现、尚未实施的提案和历史运行证据，不把计划勾选等同于实现验证。

## 3. 关键设计

### 3.1 章节版本：先修数据语义，再决定是否显示成 Git

保留现有 `ChapterPlan`、`ChapterDraft`、`CandidateDraftRecord`、`CanonCommitRecord`，不再复制一套小说数据库。

建议增补的最小语义为：稳定 chapter identity；不可变 candidate/content revision；每章当前 accepted commit 的显式指针；用于检测并发变化的 project/book revision；旧版本与替代版本的关系。

`CanonCommitRecord` 中原始章节号、原始内容身份和原始接纳结果保持可追溯。允许改变“当前是否有效”的选择关系，但不能为了新结果成立而改写旧提交的原始证据。历史 GraphDelta 保留；当前 BookState 可以按有效版本集合重建，不能把旧增量删除当成版本管理。

当前 `(project_id, chapter_number)` 全量唯一约束需要调整。实施时选定并统一使用“每章 active commit 指针 + 每章 revision 唯一”这一路径；不要同时维护负章节号、部分唯一索引和多个互相可写的 current 标记。

对于受影响的后继章节：正文不一定变化，但若新前文导致其抽取出的状态/接纳上下文变化，应产生新的接纳/投影身份，不原地改写旧提交记录的快照证据。无需给每个未改动章节复制正文文件；复用不可变内容 hash 即可。

**迁移要求：**先备份当前项目数据，在隔离副本上验证向前 Alembic 迁移；不可重写已部署 baseline、重建数据库或丢弃旧书来完成本次收敛。负章节记录只有在原始章节号可由既有审计明确恢复时才转换；来源不明则报告并暂停迁移，不猜测。旧 publisher job、receipt、candidate 和 outbox 的引用必须继续可解释。

### 3.2 发布冻结不是一个 UI 开关

| 状态 | 可否修改正式版本 | 处理 |
| --- | --- | --- |
| 普通草稿 | 可以 | 产生新候选 |
| accepted，但未发布、无不可撤销发布动作 | 可以提出修订 | 后继核验通过才切换正式版本 |
| 已排队、尚未越过外部动作边界 | 需要与发布竞争串行化 | 修订胜出则作废旧版本未执行任务；发布胜出则暂锁修订 |
| 外部发布动作进行中，或动作结果未知 | 暂时不可替换 | 根据持久 attempt/journal/reconciliation 确认结果 |
| 已确认公开发布 | 永久冻结 | 普通改稿拒绝，未来章节可以发展剧情但不能改写历史 |
| 仅上传到平台草稿箱 | 不直接视为已公开 | 更新/取消远端草稿完成核对后，才允许替换其载荷身份 |

冻结单位是章节的已公开版本；同一本书任意平台公开后即生效，不能因为主平台还没发布而替换另一平台读者已经看到的版本。删除绑定、删除任务或更改本地状态不解除已经发生过的公开发布事实。

保护字段至少包括正文、读者可见标题、章节顺序身份，以及能回溯性改变该章节世界事实的接纳/替换操作。正常在未来章节新增事实、揭示先前人物的错误认知，不属于回写旧正文。

第一次实施要求正常发布按连续章节顺序推进。对于既有跨平台乱序或中间缺章数据，保守保护已发布前缀及其依赖，不用最高章号假装整个前缀均已确认发布。

**并发实现：**发布授权与修订提交使用一致的锁顺序及持久 reservation/epoch。外部动作之前已经存在阻止版本替换的持久保护；不是浏览器即将点击时只查询一次状态。修订提交事务内重新核对内容版本、项目版本、冻结事实和未完成发布 attempt。跨越外部动作边界后仅凭 lease 到期不能认定安全。

### 3.3 历史修订：核验在接纳前，而不是保存草稿前

```text
读取当前主线版本与发布边界
→ 保存候选修订，原主线不动
→ 在隔离的候选状态中重新抽取修改章
→ 核验后续正文、状态前提和未完成叙事义务
→ 必要时修复允许修改的未发布后继，形成一个有限修订集合
→ 短数据库事务内重新确认版本和发布边界未变化
→ 原子切换整个修订集合的有效版本
→ 同事务写现有 outbox
→ 重建读投影、重新物化有效发布任务；可选导出 Git
```

P1 先检查“最早修改章到当前 accepted 尾章”的完整范围，不先建一个难以证明完整性的智能依赖图。全范围检查包括已发布后继的不可变正文；需要改变已发布后继才能成立的修订必须拒绝。新连载存稿上限会限制通常情况下的未发布后缀规模；既有超大存稿的修订超过预算时拒绝或安排受控维护，不能截断范围后宣称已验证。

核验复用现有 reviewer、实体/事实约束、人物认知、时间地点、叙事义务与 Canon gate。后续旧 GraphDelta 只能作为证据，不能因为机械重放成功就认定正文有效。

核验结果使用 pass / fail / unknown，并保存受影响范围、依据正文引用、base revision、候选 hash 与未覆盖项。fail 或关键 unknown 拒绝自动接纳本次历史修订；原版本保持有效。这一规则只加在高影响历史修订上，不新建一层每章重复 LLM 门禁。

LLM 判断不构成数学意义上的无矛盾证明。测试应证明已知硬冲突能被挡住、核验范围不会被静默缩小、失败不会污染主线；报告不能把“未发现冲突”写成“绝对不可能违规”。

### 3.4 超前生成上限

选择用户提出的 5%，只添加取整和极短作品的下限：

```text
N = 已明确的预计总章节数
B = min(N, max(3, ceil(N × 0.05)))
G = 当前 accepted 的连续章节尾号
P = 主发布平台已确认公开的连续章节尾号
R = 已持久预留、尚未 accepted 的新增章位置数（重试同一章不重复计数）
连载约束：G + R - P <= B
```

| N | B |
| ---: | ---: |
| 60 | 3 |
| 100 | 5 |
| 200 | 10 |
| 500 | 25 |
| 1000 | 50 |

例：N=200，P=40，G=48，R=1，最多还可预留 1 章，而不是再开 10 章批次。

执行规定：入队时限制批次；worker 开始新章时核对并预留；Canon 提交时复核。释放预留必须服从原任务 lease/epoch，不能释放仍在运行的同章工作。发布滞后与回执未知都不增加 P。达到上限是正常的 capacity wait，不算生成失败，不触发无意义重试，也不阻挡发布队列继续工作。

主发布平台必须是显式项目配置；只用它计算 P，避免次要平台故障拖住全部写作。冻结仍看任意平台的公开事实。主平台变更、总章数调整必须版本化并重新计算；N 调小导致存稿超限时停止新增，不删除存稿，也不自动提高 N 来逃避约束。

此限制仅适用于连载的正文生产。复用已有 `daily_serial / factory_batch / soak_test`：后两者在明确的离线/隔离任务中不受发布进度限制，且不能因此自动获得真实发布权限。不开新的小说生产入口或第二套 Pipeline。

宏观全书大纲、Arc 计划可以看得更远；5% 限制的不是思考和规划范围。反馈缺失不是等待条件。

### 3.5 小说 Git 的范围

选择“DB 决策 + Git 镜像/受控编辑入口”，不选择 Git 取代 DB，也不选择两边都可独立修改的双向同步。

P1 的 base revision、候选修订、接纳前核验已经实现用户设想中的“能否合入主线”。实际创建 Git 仓库放在 P2 最后，并以是否提供有效的差异查看/编辑收益为条件。

建议一本书一个私有本地仓库，不自动创建公开 GitHub 仓库，不把小说仓库放入 ForWin 代码仓库，不引入子模块体系。默认 `main` 由导出服务管理，只包含已接受的章节 Markdown、最小设定/计划快照和 manifest。候选分支可自由保存不完整草稿；从候选进入正式主线必须调用既有应用用例。

manifest 至少包含 book revision、稳定 chapter ID、accepted commit ID、内容 hash、base revision 及对应发布回执引用。大型 trace、原始评论、读者身份、数据库备份和凭据不进入小说 Git。

Canon 提交成功后通过已有 outbox 导出；以 book revision 去重，按版本顺序更新 Git。重试不能追加同一个业务版本的重复提交，乱序消息不能把 main 回退。Git 故障不阻断生成/发布，积压可补传。Git 丢失可以从保留的业务历史重建等价版本树；不承诺在未固定提交元数据时重新得到完全相同的 Git SHA。

用户手工编辑候选分支后，导入器只生成 proposal，不直接写 BookState。`git revert` 也是新候选，不能撤销已经向读者公开的事实。仅有文本合并无冲突并不代表故事因果正确；本地 pre-commit/pre-merge hook 可绕过，不能承担运行时强制约束。

### 3.6 一套代码、当前文档、运行收口

“一套”指一个维护中的权威源码树、一条普通构建路径；允许短期开发分支、隔离 worktree、只读历史 commit 和回滚镜像，它们不是平行维护的 runtime。

普通构建从明确 commit 全量构建角色镜像，不从旧 compat 镜像再字符串替换 Python 文件。API、generation、publisher、outbox 等角色可以不同镜像/进程，但必须追溯到同一发布源码提交和一致依赖锁。保留必要的存储与进程隔离，不把“单一源码”误解为“所有工作塞进一个进程”。

收口单位是实验批次或发布候选，不是每一章、每个短任务或整本书完结。业务 run 的 completed/failed 保持事实语义；工程上的 release closed 是另一件事，不新增一个门去篡改业务运行结果。

每次收口只做一个轻量清单：结果/版本证据已保存；修复与必要 fixture 已回主线；失败实验实现/临时开关/源码副本已删除；当前文档同步；全量构建镜像可复现并通过既有测试。下一次正式验收不依赖上一轮热修复目录。

如果正式运行途中出现 bug：在安全边界暂停受影响任务，保留原 run 证据；在隔离分支修复并测试，构建新的完整镜像；新结果使用新候选身份。生产连续性所需恢复与“无热修复验收是否通过”分开记，不靠改名抹掉中途修复事实。

文档当前树只保留 README 导航、一个当前架构入口、仍有效的专题契约、操作说明、当前未完成计划及简短决策摘要。具体阈值尽量从配置/测试引用或生成，不在多个版本文档中手抄。过期全文先确认进入可追溯 commit/tag，再从 HEAD 删除；修复链接和 Agent 默认阅读入口，避免每次检索重新读到全部历史方案。

不能删掉仍有价值的回归 fixture、测试、当前规则库或审计来源。大的历史报告可保存在已有产物存储，当前树只留必要索引与结论。“旧文档不在 HEAD”不等于改写 Git 历史，也不自动减少 Git 历史对象体积。

## 4. Stage 1：P1 修复与可靠基线

### P1-0：固定并收敛运行源码

**现有位置：**`deploy/forwin-runtime-hotfixes/`、`Dockerfile`、`README.md`、`AGENTS.md`、当前部署/CI 配置、`Design-docs/`。

**工作：**先登记主线与实际部署产物的差异；逐项确认热修复是否已经回主线。缺失修复及必要测试先归并；完整镜像验证后才删除常规路径对 compat/hotfix 的依赖。保留只读回滚证据，不先删掉唯一可工作的恢复材料。更新当前架构说明与 Agent 入口，并在既有 CI/发布检查中拒绝新的生产源码镜像副本和运行时源码替换路径。

**验收：**从已记录 commit 的干净 checkout 可以构建本轮运行产物；不需要 11 个历史补丁目录参与装配；源码/镜像/策略身份可核对。不把仅编译成功当成兼容恢复已通过。

### P1-1：版本身份与发布冻结

**现有位置：**`forwin/models/canon.py`、`forwin/models/draft.py`、`forwin/models/project.py`、`forwin/canon/admission.py`、`forwin/canon/historical_rewrite.py`、`forwin/application/projects/reviews.py`、`forwin/publisher_runtime/canon_jobs.py`、`forwin/publisher_runtime/attempts.py`、`forwin/publisher_runtime/receipts.py`、`forwin/migrations/`。

**工作：**实现稳定章节身份与 active revision；替代负章节归档；补齐冻结查询与最终提交约束；发布任务携带不可变内容身份并与修订竞争串行化。受保护发布过程的锁与 reservation 复用现有持久任务语义，不靠内存布尔变量。

**必须覆盖：**已发布 retry 被拒绝；只上传草稿不伪称公开；多平台任意一处公开即冻结；远端已发生但回执丢失仍不可改；修订与发布并发只能一个取得对应动作资格；旧版本 pending job 不被误发；任务删除或重启不能解除永久冻结；向前迁移保持全部历史引用有效。

**验收：**通过 API/MCP/worker/Canon 入口都无法绕过冻结。迁移前后章节身份、发布内容 hash 和既有 receipt 不丢失；所有现存副本问题有明确处置，不静默推断。

### P1-2：后继一致性核验与原子替换

**现有位置：**`forwin/canon/historical_rewrite.py`、`forwin/canon/admission.py`、`forwin/canon/plan.py`、`forwin/book_state/`、`forwin/review/`、`forwin/outbox/`。

**建议新增：**仅在需要独立 owner 时增加 `forwin/canon/revision_validation.py`，承载修订范围、基线身份、核验结果和现有检查器调用；不要新建独立 supervisor 运行进程。

**工作：**候选阶段不重置主线；从修改点前的有效状态构建隔离核验；验证完整后继区间；原子切换合法的修订集合；所有外部动作只在切换后通过 outbox 发生。提交前检查 base revision 与冻结/发布边界；过期则拒绝或重新评审，不能复用过期 pass。

**必须覆盖：**删钥匙导致后继开门不成立；改变人物知情状态；改变死亡/存活状态；改变时间地点；纯措辞变更仍被核验而不是由用户标签免检；核验超时/unknown；后继被另一个任务更新；发布在核验期间完成；事务任一阶段失败；旧 accepted 主线在所有失败场景下完全保持有效。

**验收：**旧增量可重放不再被当成完整核验通过；原始正文与提交证据保持历史；不产生半套新主线，不出现未核验后继被静默接纳。

### P1-3：5% 存稿与一致预留

**现有位置：**`forwin/production/policy.py`、`forwin/production/planner.py`、`forwin/production/backlog.py`、`forwin/production/scheduler.py`、`forwin/long_run_policy.py`、generation 应用/worker 路径、publisher 回执读侧。

**工作：**按第 3.4 节公式计算，入队、执行和接纳的责任明确分层。批量任务只执行取得预留的新增章节，失败重试不重复消耗；达到上限不触发失败修复。生成等待不能使同一规划器不再安排已有可发布内容。复用现有生产模式，不新增第二个 scheduler。

**必须覆盖：**N=100/B=5；P=0；多 worker 抢最后一个名额；任务在预留/接纳边界崩溃；发布到第 5 章但第 3 章结果未知；主次平台不同进度；N 下调；已有存稿超过新上限；离线 long run 不因 P=0 卡住；daily_serial 没有评论仍能随确认发布继续写。

**验收：**新预留不越上限；超限历史存稿不丢失；等待原因可见且发布能继续推进；确认回执与“已请求发布”不混用。

### P1-4：自主长篇验收与阶段收口

**现有位置：**`forwin/runtime/policy.py`、持久 generation task 与 worker、review/repair、现有长跑 harness 和测试。

**工作：**明确本轮自动化使用的有效策略。当前 standard 默认有人工 checkpoint/pause 设置；使用现有支持的策略字段配置自动运行，不通过隐藏全局参数或 request override 改行为。可恢复基础设施故障自动恢复；内容硬失败先走有限 repair，耗尽则可解释停止。已经成功的 Canon 不因任务恢复重复执行。

**验收分两类：**

- 生产能力：先以约 20 章做排障 smoke；锁定源码/模型/策略后，使用一部全新 100 章离线项目做本阶段长跑。要求无中途源码修改、无人工逐章放行，并能完成既定收尾目标，而不只是凑足 100 个 accepted 行。失败如实记录并修成因，不追加无限新门禁。该结果仅证明该配置/样本，不证明跨题材文学生成普遍成功。
- 连载安全：用隔离 publisher 测试适配器验证冻结、5% 与回执/重启/并发组合；测试回执不能写入生产或当作真实外部发布成功。真实平台 smoke 单独列出，需使用已明确授权的作品与发布方式；不为做测试自动公开新作品。

每个小任务先运行其针对性测试，再跑相关现有回归；阶段末跑同一主线的全量 suite。长跑只在阶段候选上执行，不要求每个小改动重跑百章。

本路线图实施时要明确取代旧路线图中与它重复的长跑要求；不要把旧 L200、所有历史矩阵与本次 L100 机械叠加成更多前置门。更长稳定性测试可另列版本发布验证，但不是评论 P2 的隐性前置条件。

**Stage 1 完成定义：**单一可构建基线；冻结与历史修订契约成立；5% 正确；无评论长篇生产取得明确样本证据；未通过项未伪称完成；当前文档一致。

## 5. Stage 2：行为保持重构与消融实验

### A0：先拆职责，不改结果

**现有位置：**`forwin/generation/pipeline.py`、`forwin/generation/pipeline_core/`、`forwin/review/repair/`、`forwin/runtime/`。

当前 Pipeline 用 12 个 Stage 基类共享对象。先以现有契约测试固定行为；逐步把跨 Stage 绑定回调收为有限输入/输出与明确服务。优先隔离 Writer 执行、Review/Repair 和 Canon 准备的职责；Pipeline 保留顺序协调与任务控制，不再通过完整 self 或等价的万能回调袋提供全部能力。

这不是强制凑某个类数，也不以缩短单文件行数作为验收。不要新建一层抽象门面却保留全部旧入口。每次迁移替换真实调用方并删除旧路径，保证异常、暂停、幂等及 outbox 语义不变。

**验收：**相同固定输入/模拟响应得到相同业务结果；一个 owner 能在不构造整个 Pipeline 的情况下测试；没有新增运行 mode 或第二套 Canon 入口。

### A1—A4：一次只改变一项假设

| 实验 | 可证伪的问题 | 允许试验的变化 | 禁止删掉的边界 |
| --- | --- | --- | --- |
| A1 重复语义评审 | 某个额外 reviewer 是否只重复已有结论 | 每次只移除一个已确认重叠的语义检查，保留独立标注对照 | 发布冻结、实体身份、Canon 事务、历史修订必要核验 |
| A2 重复上下文/投影 | 同一事实的多份输入是否增加 token 与冲突而无质量收益 | 从 Writer 输入中逐项撤掉冗余来源；单独评估是否还需维护该投影 | 唯一 Canon，以及有真实消费者且不可替代的检索能力 |
| A3 post-Canon 维护频率 | 每章 world simulation/某维护步骤是否必须强同步 | 先证明下游能使用有版本的旧结果，再试 band 边界/事实变化触发 | 未证明可陈旧的数据依赖、前后章顺序、必要计划准备 |
| A4 Scene→stitch | 多阶段正文生成是否显著优于单章一次生成 | 隔离实验分支使用单章 writer，评审/接纳边界不变 | 不永久保留第二套 writer 或兼容回调层 |

A3 不能直接删除现有四步 barrier；它需要先通过消费者依赖验证。A4 只有在前面数据表明 Writer 调用成本/一致性值得优化时进行，不为了完成表格强行重写 Writer。

### 样本与判断

先用冻结正文、合同、模型响应做离线重放，覆盖已知正确与已知错误样本。只有出现可解释收益的方案才使用真实模型：建议每个候选 3 种题材 × 2 个起点 × 各续写 3 章，共 18 章；基线使用相同起点、上下文、预算和模型设置。模型 seed 不被当作跨调用可重复性的保证。

记录成本/实际 token、耗时、修复次数、正确 hard blocker 的保留情况、人工介入次数、连续性错误、叙事完成度和盲评偏好。旧 reviewer 的输出不是唯一标准答案；使用独立标注的约束与正文证据。

默认采用工程筛选线：出现已知严重漏拦则拒绝；没有严重退步且成本或延迟减少至少 15% 才优先考虑上线；纯结构收敛可基于等价行为与维护边界改善成立，不强求性能提升。15% 是本计划选择的筛选阈值，不是研究结论。18 章是筛选样本，不构成统计上证明普遍等价。

结果可为保留、删除或证据不足。证据不足时不新增更复杂的模块；要么保留既有实现，要么停止该实验。不得通过调低质量阈值制造成本胜出。

**Stage 2 完成定义：**每项运行过的实验有结论及来源；胜出实现进入唯一主线；失败分支只保留在历史；临时 flag、对照源码副本和无真实调用的接口从当前树删除；全量回归通过；保留下来的硬边界没有被削弱。

## 6. Stage 3：P2 反馈闭环与可选小说 Git

### P2-1：评论归属与完整消费

**现有位置：**`forwin/simulation/world.py`、`forwin/audience/feedback.py`、`forwin/models/publisher.py`、publisher 评论摄入路径、`tests/test_audience_feedback_alignment.py`。

分开保存评论所指的 remote chapter/本地 chapter identity/发布版本、评论发生时间、摄入时间、分析时间及分析时的生成进度。平台无法提供可靠对应关系时保存 unknown，不按当前生成章号填充；跨章证据只能用可确认的来源章节。

待分析查询先筛出未完成分析的评论再分页，不用“最新 N 条”代表待处理队列。每条评论即使零信号，也记录该分析器版本完成；失败重试有有限次数和可见错误。分析器版本变化可安排明确重算，不把已存在任意一个 signal 当成永远完成。

幂等去重至少使用平台/账号或绑定范围/作品/远端评论身份；按平台区分作者身份，未知作者不冒充多个确认用户。编辑过的评论由原内容 hash/版本检测，避免同一 ID 内容变了却永不重分析。

**验收：**100 条/每批 8 条全部最终处理；零信号不死循环；乱序/分批摄入不改变来源章节和去重结果；对历史评论的回补不被伪装成新章节共识；书籍同名不混入另一项目。

### P2-2：聚合、行动与 Writer 提示同源

**现有位置：**`forwin/audience/feedback.py`、`forwin/audience/actions.py`、`forwin/simulation/world.py`、`forwin/state/repo.py`、`forwin/context/providers/feedback_provider.py`、现有 planning 消费方。

让评论分析产生带证据与方向的结构化信号；窗口聚合拥有唯一计算逻辑；行动映射拥有唯一决策逻辑；Writer/规划/界面只消费对应读视图，不各自重算一遍等级或行动。

修复 prediction 的 Writer 提示漏接；区分快/慢、正向热度/负向风险等目标方向；响应范围、提示有效期、重复触发冷却期分开。提示裁剪之后才记录哪些进入了输入。建议生成、被选用、进入计划/Writer、正文落实与观察到的后续变化分开，不把 proposed 记录称为已执行。

只增补现有 `FeedbackActionRecord` 所需字段和关联，不新建多层反馈总控框架。行动效果命名为“前后信号变化/关联观察”；明确样本不足、发布版本不同和时间窗口重叠，不能当成因果收益。

修正聚合 denominator：评论总数不能只统计产出 signal 的评论；同一评论对同一信号不要多次放大 hit；跨平台身份与低置信度来源不能悄悄提升共识等级。

**验收：**六种现有信号有确定的消费或明确观察路径；方向相反得到适当不同动作；不存在未传给下游却被统计为已落实的行动；只有明确来源和足够证据的信号进入自动改纲。

### P2-3：一个有限而完整的反馈迭代样本

复用版本化 Planning 与 P1 修订入口，将一次编辑决定关联到来源评论/聚合快照、目标章节范围、计划版本和实际内容版本。

使用低热度、迟到、互相矛盾和单一读者反复催更的输入。没有可靠共识时按既定计划继续，不为迎合单条评论更改根设定。验证“处理读者反馈”不会推翻发布冻结，也不让无评论项目卡死。

**验收：**至少一个可追溯样本完成评论→决定→未来计划/未发布修订→正文→后续观察；同时完成一个合理拒绝修改的样本。前后观察不伪称证明留存提升。

### P2-4：小说 Git，可选并最后执行

**现有位置：**现有 outbox、artifact storage、candidate/proposal 应用入口；导出器按第 3.5 节实现。

先提供单本书 Markdown + manifest 导出并演示版本差异；只有确实需要 Git 的浏览/编辑工作流才增加每书 Git 仓库管理。接纳前核验不依赖这个任务完成。

**验收：**相同 book revision 重试不重复导出；乱序消息不回退主线；Git 不可用时 Canon/生成/发布正常；远端默认私有且不自动发布；修改分支通过 proposal 导入而非直改 Canon；已发布内容无法通过 revert/merge 绕过冻结；原始评论和凭据不进入仓库。

**Stage 3 完成定义：**反馈数据语义与消费可靠，计划/内容应用可追溯，无评论时仍可自主生成；可选 Git 不产生第二套接纳规则或不可恢复的同步依赖。

## 7. 实施与验收纪律

每个工作包在隔离开发分支中先写最小失败复现，再实现，再跑针对性与相关回归；schema、代码、测试和当前契约一起评审。行为保持重构与行为改变分开提交。不要因手工测试一条 happy path 通过而删除异常/并发测试。

本轮计划没有运行以下命令。它们是实施后的基础验证入口，使用项目已经配置的隔离 PostgreSQL/依赖环境：

```bash
python -m pytest -q
ruff check forwin tests
python -m compileall -q forwin
# 额外执行每个工作包新增的针对性测试、迁移恢复验证和相关发布/worker 测试。
```

每一轮只保存轻量证据：源码 SHA、镜像 digest、有效策略/模型、输入快照、结果和失败分类。不增加外部签名系统、通用审批引擎或复杂“验收的验收”脚本。现有可靠回执、内容 hash、lease fencing 与事务注入测试继续保留。

本计划不自动授权修改现有生产作品、执行真实发布、创建公共小说仓库或清理历史数据。真正实施涉及这些外部写操作时，沿用明确的作品/环境范围和既有安全流程。

## 8. 明确不做

本轮不把 Git 变成 Canon 数据库；不做双向自动同步；不建独立状态监督 Agent；不重写整套工作流；不训练评论推荐模型；不把读者数量作为生成条件；不为支持修订实现任意深度的多宇宙小说分支；不把全部历史报告与数百个运行检查继续堆在当前文档；不把每一个小补丁都绑到新的全书重跑。
