## 正式历史读取

待审修订曾挤占摘要 SQL 窗口，并把正式评审替换成最新候选的 unknown。现先按稳定章节选窗口，再沿 active Canon 找正文及 candidate 绑定的评审；上下文、Arc、节奏分析和 Band 核验采用同一合同。保存或拒绝修订时正式输入不变，完整后缀核验通过并实际接纳后才切换。

accepted 缺少身份时，正文 API 返回 409，列表仍保留 accepted 及历史记录；Band 缺正文或绑定评审仍阻断。未接纳章节的最新草稿读取不变。空摘要保持空值，不以计划概要或旧稿摘要补造新事实；修订生产端是否生成新摘要不由读侧测试证明。

真实 PostgreSQL 回归覆盖实际 Canon 接纳、API/MCP 读取、StateContextProvider、Arc、节奏重规划和 Band 阻断。读侧包相关 107 项、控制消费者相关 141 项通过，另有独立审查及 13 项正式历史回归；这些范围重叠，不相加当全量结果。

以上第一组修复已提交为 `40bec1f`。随后独立审查发现旧自动 Band checkpoint 会直接复用历史 PASS，跳过上述新读侧：真实修订接纳后，当前正文已不满足原合同，仍返回原 checkpoint。原规则重新计算应产生 WARN，标准 `pause_on_warn` 会暂停；本轮保留这一严重度。

原有七处确定性检查已移到同一 `BandCheckpointEvaluator`，输入收集同时供计算与指纹使用，既有创建事件保存证据。相同输入复用；相关正文、接纳身份、计划、义务及约束变化后，旧 PASS/override 失效，重评追加记录，旧记录和事件保留。缺失或损坏的旧证据不能授权。维护、直接推进、读模型、继续生成及人工/Spark 批准使用同一合同；Spark 模型返回后在短项目锁内复核输入，改变时不 override。

同一事务的创建时间可能相等，不能靠随机 UUID 选择新核验；新记录在项目锁内使用严格递增的创建时间。历史修订中复用正文的后继维护以 active Canon 链核对身份，不要求覆盖旧 candidate backref。已成功的维护只重评失效的确定性 checkpoint，不重复模型；行锁竞争返回 Busy，不写成业务失败。实际写作调用方在 manual-start、计划审查和 Writer 前提交这段短事务，避免把项目锁带进模型调用。

`continue` 仍按原策略跳过自动检查：从未创建 checkpoint 时下一 Band 不再等待它；已有有效 FAIL、ERROR 或未接纳前章仍阻断。新增真实 PostgreSQL 回归为核心 23 项、批准/继续/委托 13 项、实际写作调用链 3 项。相关组合 114 项、入口组合 139 项及 6 个子测试通过；根代理组合 117 项通过，独立入口与调用链审查 16 项通过。范围重叠，模型与 enqueue 使用明确边界替身，不作为真实长跑证明。三个旧 FakeSession 测试改用既有 SQLite durable harness，保留原拒绝原因和断言。

## 世界编辑接纳边界

局部 BookState gate 和人工强制批准不足以核验 accepted 后继正文。独立 PostgreSQL 复现还表明，未来章节的重命名或回填义务可能改变历史读取共用的实体数据，不能只比较 envelope 章号。
